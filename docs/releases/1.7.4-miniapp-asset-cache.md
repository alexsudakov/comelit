# 1.7.4 — Mini App frontend cache-busting

Status: **release-ready / production canary required**

## Observed on 1.7.3

Telegram Desktop/laptop showed a mixed state:

- new JavaScript behavior was active: the transport label correctly stayed `HLS`;
- before the first HLS frame, the viewer was compact;
- once video started, the media surface expanded far beyond the intended compact viewport.

Because the Mini App bootstrap document is served with `Cache-Control: no-store`
while local JavaScript and CSS are separate static resources, a WebView/browser
can retain one frontend asset across integration updates while fetching another
fresh asset.

## Fix

- all local Mini App frontend resources now include a release-version query
  string in `index.html`;
- the explicit video stage additionally uses layout/paint/size containment,
  forced clipping, and width bounds.

This makes each release request a fresh stylesheet/host/card URL and prevents
new JavaScript from running against stale Mini App CSS.

## Unchanged

- WebRTC/HLS transport behavior from 1.7.2 is unchanged;
- no camera preload;
- no Frigate dependency;
- Comelit entrance-camera media lifecycle is unchanged;
- Door/Gate behavior is unchanged.

## Canary

After upgrading to 1.7.4 and restarting Home Assistant:

1. fully close the Telegram Mini App;
2. reopen it;
3. open `Паркинг 6048`;
4. verify that the video remains inside the compact fixed stage before and
   after the first HLS frame;
5. verify the label remains `HLS` after HLS fallback.
