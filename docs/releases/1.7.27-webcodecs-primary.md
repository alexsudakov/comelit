# Comelit 1.7.27 — Entrance WebCodecs primary viewer

## Purpose

Release 1.7.27 promotes the direct Entrance WebCodecs/WSS path introduced and
live-accepted in 1.7.26 from an explicit diagnostic canary to the normal
Telegram Mini App Entrance camera viewer.

The production Mini App path is now:

```text
explicit "Показать камеру"
  -> existing Mini App auth/session boundary
  -> embedded WebCodecs viewer
  -> /api/comelit/miniapp/camera/camera.comelit_entrance/webcodecs
  -> one miniapp_webcodecs lease
  -> existing ComelitMediaSessionManager
  -> existing listener pause / exclusive on-demand media ownership
  -> existing native Entrance media helper
  -> existing H264RecoveryRtpShim
  -> /run/comelit-media/local-rtp.sdp
  -> PyAV SDP/RTP demux only
  -> H.264 Annex-B access units
  -> bounded WSS protocol v2
  -> Telegram Android WebView VideoDecoder
  -> canvas
```

No second P2P session, CTPP session, media owner, transcoder or permanent
application service is introduced.

## Primary transport and fallback

For the normal Entrance viewer:

```text
PRIMARY = WebCodecs/WSS
FALLBACK = existing Home Assistant HLS viewer
```

The embedded production viewer starts automatically after the user explicitly
opens the Entrance camera. It does not expose the diagnostic camera selector,
`Запустить тест` button, Stop button or canary result block.

A bounded 15-second first-decoded-frame startup deadline protects the primary
path. Unsupported WebCodecs, decoder setup failure, WSS/source startup failure,
or other terminal startup/runtime errors switch the card automatically to the
legacy HLS viewer.

The fallback does not start a parallel Comelit session. Before requesting HLS,
the server waits for an in-flight `miniapp_webcodecs` ownership teardown to
reach a safe inactive state. Manager error, ownership conflict or bounded
cleanup timeout fails closed instead of creating overlapping media ownership.

This cleanup synchronization is not an automatic Comelit protocol retry.

## Stable viewer lifecycle

A healthy embedded Entrance WebCodecs viewer is preserved across unchanged
card renders and normal Home Assistant state refreshes. The card therefore does
not destroy a working WSS session merely because unrelated entity state changed.

When a prior embedded viewer really is replaced, the next Entrance WebCodecs
open synchronizes with the previous `miniapp_webcodecs` teardown before the
single manager acquire. This prevents a transient self-generated
`intercom_media_busy` race without repeating a Comelit operation.

## Session limits

The existing `ComelitMediaSessionManager` remains authoritative for the
Entrance media lifetime and its 600-second absolute hard ceiling.

The diagnostic ordinary-camera WebCodecs path retains its existing shorter
limit. The old 60-second Entrance canary timer is not used by the embedded
production viewer.

There is still no automatic Comelit media retry.

## Debug WebCodecs tab

The diagnostic WebCodecs tab and canary UI remain in the integration for future
controlled tests but are hidden in normal production use.

The default Mini App surface remains:

```text
[ Домофон ] [ Видеонаблюдение ]
```

The diagnostic tab is exposed only with the explicit URL query flag:

```text
webcodecs_debug=1
```

Opening the debug surface still does not itself start media; its explicit
canary controls are retained.

## Security and media boundary

The 1.7.26 security and zero-transcode boundaries are preserved:

- Mini App authentication/session validation is unchanged;
- only the exact Entrance camera is admitted to the intercom WebCodecs path;
- Gate and other Comelit camera identities remain rejected;
- source SDP/path and credentials remain server-side;
- PyAV performs SDP/RTP demux and H.264 representation normalization only;
- no server-side video decode, encode, re-encode, scale or filter is added;
- WSS protocol v2 framing remains closed and bounded.

## Door and Gate

Door and Gate semantics are unchanged.

```text
DOOR_ACTIONS_FROM_MEDIA_START=0
GATE_ACTIONS_FROM_MEDIA_START=0
automatic_retry=false
```

The release does not promote any new Gate actuation profile and does not infer a
physical Door/Gate effect from protocol completion.

## Deployment boundary

Publishing the release does not itself restart Home Assistant.

After installation/deployment, Home Assistant must load the new frontend/runtime
files before production acceptance. Any explicit Home Assistant restart remains
subject to the project's separate `restart USER_APPROVED` authorization
boundary.

No Door/Gate action or additional live Comelit canary is required by release
preparation itself.
