# 1.7.7 — Mini App WebRTC media deadline after slow signaling

Status: **release-ready / production canary required**

## Confirmed by the 1.7.6 production canary

For `camera.parking_6048`, signaling completed but consumed almost the entire
five-second zero-RTP budget:

- `answer`: 4778 ms from viewer start;
- remote video `track`: 5028 ms;
- first observed `ICE checking`: 5278 ms;
- fallback: 5970 ms with `stats_deadline_checking`;
- inbound video RTP remained 0 bytes / 0 decoded frames.

The previous implementation measured the 5/8-second zero-RTP threshold from
`_openWebRTC()` start. In this canary, ICE therefore had less than one second
after the remote track arrived before the client forced HLS fallback.

This evidence proves premature client fallback. It does not prove that ICE
connectivity itself would have failed if allowed to continue.

## Fix

The WebRTC startup now has two independent bounds:

- signaling without a remote stream: unchanged 6000 ms timer;
- zero-RTP media wait after a remote video track arrives:
  - 5 seconds while ICE is `new`, `checking`, `disconnected`, or `failed`;
  - 8 seconds otherwise.

The media deadline starts when first-frame monitoring starts for the remote
video track. Diagnostic `elapsed_ms` remains measured from the beginning of
the viewer session, so production traces remain comparable across releases.

## Regression coverage

A browser regression reproduces approximately 4.8 seconds of signaling delay,
then starts a zero-RTP `checking` track:

- no fallback is allowed around the old total-session six-second boundary;
- fallback is still required after five seconds of actual media wait.

The architecture contract also requires an explicit media-start clock and the
5/8-second thresholds to use that clock.

## Scope

This release does not:

- change the 6000 ms signaling timeout;
- change HLS implementation or HLS startup behavior;
- enable camera preload;
- change the Comelit entrance-camera lifecycle;
- change Door/Gate behavior.

A new production canary is required after installation. If ICE still remains
`checking` with zero RTP after a full five-second media window, the next
investigation should focus on candidate-pair connectivity/NAT rather than
client timeout accounting.
