# Comelit 1.7.25 — WebCodecs live corrective

## Purpose

Release 1.7.25 is a corrective follow-up to the first production run of the
experimental Telegram Mini App WebCodecs path introduced in 1.7.24.

The first live run proved that the zero-transcode H.264-over-WSS path can render
smoothly in Telegram Android WebView, but also exposed two diagnostic/UI defects:

1. periodic Mini App Home Assistant state refresh rebuilt the WebCodecs viewer
   DOM while idle, closing the camera dropdown and resetting result scrolling;
2. the 1.7.24 `ACCUMULATED_LAG` metric mixed camera/PyAV PTS progression with
   browser arrival progression and therefore could not be interpreted as
   WSS/CloudPub backlog.

This release fixes those defects without changing the existing production
MSE/WebRTC/HLS camera paths or the Comelit Entrance media lifecycle.

## 1.7.24 live evidence

Observed bounded run:

```text
ENTITY_ID=camera.dvor_1
RESULT=PASS
ZERO_TRANSCODE=true
DURATION_S=58.3

WS_CONNECT_MS=156.3
FIRST_DECODED_FRAME_MS=5784.6

UNITS_RECEIVED=599
FRAMES_DECODED=599
KEYFRAMES_RECEIVED=12
SEQUENCE_GAPS=0

DECODE_P50_MS=5.3
DECODE_P95_MS=16.4

MAX_DECODE_QUEUE=14
BACKLOG_STOP=false
DROPPED_UNITS=0
```

User observation: video appeared quickly once the source started and remained
smooth without visible stutter.

The intended `camera.parking_6048` target was not actually selected. Because
the viewer DOM was rebuilt during periodic state refresh, the select dropdown
closed and the effective run remained on `camera.dvor_1`.

## Stable WebCodecs UI lifecycle

The WebCodecs viewer now avoids full `shadowRoot.innerHTML` replacement for
ordinary background HA-state updates.

Camera lists are compared by a stable semantic fingerprint:

```text
entity_id + display name
```

When that list has not changed, the existing select/result/canvas nodes remain
mounted.

The corrective preserves:

- current camera selection;
- an open/select interaction across background refresh;
- result scroll position;
- the last rendered canvas frame after Stop;
- existing canvas/result node identity during an active run.

Buttons, status and counters are updated in place.

A new explicit Start clears the previous result, which is the only normal point
where the canary result is intentionally reset.

## WebCodecs binary protocol v2

The frame header is extended from 20 to 36 bytes:

```text
offset  size  field
0       1     uint8   protocol_version = 2
1       1     uint8   KEY / DELTA / PTS_VALID flags
2       2     uint16  reserved = 0
4       4     uint32  sequence
8       8     uint64  media_pts_us
16      8     uint64  source_elapsed_us
24      8     uint64  send_elapsed_us
32      4     uint32  payload_length
36      N     bytes   H.264 Annex-B access unit
```

`source_elapsed_us` is measured using the Home Assistant monotonic clock from
the first H.264 access unit received by the adapter.

`send_elapsed_us` is measured using the Home Assistant monotonic clock from
the first binary WebSocket send.

The camera media PTS remains a separate clock domain.

No wall-clock synchronization between Home Assistant and the phone is required.

## Corrected drift metrics

The ambiguous 1.7.24 `ACCUMULATED_LAG` field is removed from the current
canary result.

Protocol v2 reports three independent relative drift domains:

```text
SOURCE_PTS_DRIFT
  = HA source receive elapsed
  - camera media PTS elapsed

SERVER_QUEUE_DRIFT
  = HA send elapsed
  - HA source receive elapsed

TRANSPORT_DRIFT
  = phone binary receive elapsed
  - HA send elapsed
```

The metric relevant to WSS/CloudPub accumulation is `TRANSPORT_DRIFT`.

`SOURCE_PTS_DRIFT` is intentionally separate because a camera's media PTS may
advance at a cadence that differs from wall-clock packet arrival.

No hard transport-latency threshold is encoded in the canary. The result now
separates:

```text
FUNCTIONAL_PASS=true|false
TRANSPORT_BACKLOG_OBSERVED=unknown
```

The measured transport drift is interpreted after the run rather than being
forced through an invented threshold.

## Distinct startup milestones

The server now emits separate bounded control markers for:

```text
source_open
source_packet
```

The client reports distinct:

```text
WS_CONNECT_MS
SOURCE_OPEN_MS
FIRST_SOURCE_PACKET_MS
FIRST_BINARY_MS
FIRST_DECODED_FRAME_MS

SOURCE_STARTUP_MS
SOURCE_PACKET_TO_BINARY_MS
BINARY_TO_DECODE_MS
```

`SOURCE_OPEN_MS` corresponds to successful return from the H.264 source open
boundary. `FIRST_SOURCE_PACKET_MS` corresponds to the first real non-empty
H.264 access unit.

These are diagnostic startup stages; they are not asserted as physical
glass-to-glass latency.

## Safety and scope

The corrective does not change:

- ordinary production MSE playback;
- WebRTC fallback;
- HLS fallback;
- Comelit Entrance camera lifecycle;
- persistent listener lifecycle;
- Door/Gate behavior.

The experimental WebCodecs path still rejects the Comelit Entrance camera.

No automatic live retry is introduced.
