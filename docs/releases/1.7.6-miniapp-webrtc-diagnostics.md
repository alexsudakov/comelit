# 1.7.6 — Mini App WebRTC/HLS startup diagnostics

Status: **release-ready / production canary required**

## Purpose

This release promotes the bounded diagnostics added after the 1.7.5 external-camera startup investigation. The goal is to capture enough evidence from the Telegram Mini App to distinguish ICE negotiation failure, missing inbound RTP, track/frame timing, and HLS fallback behavior without logging SDP, candidate strings, addresses, tokens, URLs, cookies, Telegram init data, or media payloads.

## Runtime changes

- Adds the authenticated camera diagnostics endpoint used by the Mini App.
- Reports bounded WebRTC milestones for config, offer/answer, track, ICE, RTP, first frame, fallback, and HLS startup.
- Starts a read-only `getStats()` diagnostics sampler when the peer connection is created, so ICE/candidate-pair and RTP state can be observed before a remote `track` arrives.
- Keeps client diagnostics bounded and throttled, with terminal navigation fallback reported immediately.
- Enforces server-side per-session and per-camera event limits with bounded limiter state and fixed HTTP 429 response `diagnostics_rate_limited`.
- Keeps delayed events tied to the original camera entity and generation so they cannot leak into a later viewer session.
- Keeps client and server diagnostics counter budgets aligned at 16.

## Safety and compatibility

The existing playback policy is unchanged:

- ICE-checking fallback threshold remains 5 seconds when video RTP stays at zero.
- General zero-RTP fallback threshold remains 8 seconds.
- The existing 6000 ms signaling timer is unchanged.
- No camera preload is enabled.
- No Comelit Door/Gate behavior is changed.
- No entrance-camera media lifecycle ownership rule is changed.
- Diagnostics reject free-text and sensitive-looking values and never echo rejected payloads.
