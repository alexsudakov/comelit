# Comelit 1.7.22 — use direct Generic Camera RTSP source for Mini App MSE

## Production evidence

The 1.7.21 live capture showed that the MSE request reached HA-managed go2rtc
almost immediately, but neither configured producer had completed startup before
the Mini App deadline:

```text
mse_negotiation_forwarded       ~58 ms
stream_state_250ms              producers=[{},{}], consumers=null
stream_state_4000ms             producers=[{},{}], consumers=null
stream_state_7000ms             producers=[{},{}], consumers=null
mse_fallback                    8001 ms
```

No upstream go2rtc `type=error` response was emitted.

## Root-cause direction

Upstream go2rtc handles a `ffmpeg:` source by redirecting it to an `exec:`
producer. For RTSP output, that exec path launches ffmpeg and waits for ffmpeg
to connect back to go2rtc's internal RTSP server.

The upstream exec module uses a default startup timeout of 30 seconds.

The Mini App MSE negotiation budget is deliberately bounded to 8 seconds, so a
cold Generic Camera ffmpeg/exec producer can remain unresolved for the entire
MSE attempt without producing a go2rtc WebSocket error.

## Change

For Mini App MSE only, ordinary Generic Camera entities now use the validated
public Home Assistant camera source directly:

```text
await camera.stream_source()
-> rtsp://...
-> HA-managed go2rtc
-> restricted Comelit MSE WebSocket proxy
```

Previous MSE registration for Generic Camera:

```text
ffmpeg:<rtsp source>
ffmpeg:<internal stream>#audio=opus#query=log_level=debug
```

1.7.22 registration:

```text
<rtsp source>
```

The RTSP source remains entirely server-side. It is never serialized to the
Telegram Mini App, diagnostics payloads, or browser-visible URLs.

## Scope

This change applies only to the Mini App MSE source registration path.

Home Assistant's own WebRTC provider is unchanged. If MSE fails, the existing
fallback still enters Home Assistant's registered WebRTC path and therefore
retains Home Assistant core's own Generic Camera compatibility behavior.

The ordinary-camera fallback order remains:

```text
MSE -> WebRTC -> HLS
```

## Why this test is different from 1.7.14

1.7.14 also used a direct source, but that release still had several independent
startup defects:

- the old Home Assistant go2rtc runtime/session handling;
- generic H.264/H.265 codec tokens instead of actual browser MSE codec IDs;
- a 3 s absolute MSE deadline rather than stage-relative deadlines.

1.7.22 tests direct RTSP with the later corrected runtime, codec negotiation,
8 s stage deadlines, server milestones, go2rtc state snapshots, and upstream
go2rtc error logging.

## Unchanged behavior

1.7.22 does not change:

- Mini App browser MSE protocol;
- MSE deadline values;
- WebRTC fallback;
- HLS fallback;
- 1.7.21 diagnostics;
- Comelit entrance-camera lifecycle;
- Door/Gate paths.

The strongest success path is:

```text
mse_negotiation_forwarded
-> mse_upstream_reply

-> mse_ready

-> mse_first_frame
```

If direct RTSP fails, the existing `COMELIT_MINIAPP_DIAG_GO2RTC_WS` and
go2rtc state snapshots should now expose the direct producer's actual failure
or media/consumer state without the ffmpeg/exec startup layer.

No Door or Gate action is required.
