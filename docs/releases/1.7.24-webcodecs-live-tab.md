# Comelit 1.7.24 — experimental Mini App WebCodecs live tab

## Summary

Release 1.7.24 adds an experimental Telegram Mini App-only live-view path for
ordinary allowlisted Home Assistant cameras.

The new path is intentionally isolated from the existing production camera
viewer and is used to measure whether low-latency H.264 delivery over the
existing HTTPS/WSS ingress is suitable before changing the production media
architecture.

The tested transport shape is:

```text
Home Assistant camera
  -> camera.stream_source()
  -> H.264 demux/repackaging only
  -> Annex-B access units
  -> bounded binary WebSocket
  -> existing HTTPS/WSS / CloudPub ingress
  -> Telegram Android WebView
  -> WebCodecs VideoDecoder
  -> canvas
```

## Scope

The WebCodecs tab is shown only when the Mini App explicitly enables it.

Normal Home Assistant / Lovelace use of the shared Comelit card remains
unchanged and keeps the existing tabs and playback behavior.

Opening the WebCodecs tab does not open a camera. A source is opened only after
the user explicitly presses the start button.

The first intended production canary is:

```text
entity=camera.parking_6048
duration=60s
automatic_retry=false
```

The entity is not hard-coded in the implementation; any permitted ordinary
camera with a compatible H.264 RTSP source can use the experimental path.

## Zero-transcode boundary

The server source adapter uses PyAV only to open/demux the RTSP source and
normalize H.264 packet representation.

The path does not decode, encode, re-encode, scale or filter video.

It also does not use:

- HLS;
- MSE;
- fMP4;
- WebRTC;
- the normal go2rtc MSE media path.

AVCC and Annex-B input are normalized to Annex-B. SPS/PPS are prepended to
keyframes when required, and the WebCodecs codec string is derived from SPS
rather than hard-coded.

Home Assistant's `stream` dependency provides the pinned `av` runtime used by
this adapter. Import remains lazy and a missing dependency fails boundedly with
`source_dependency_missing`.

## WebSocket protocol

Each binary message contains exactly one H.264 access unit with a bounded
versioned header:

```text
offset  size  field
0       1     uint8   protocol_version = 1
1       1     uint8   KEY / DELTA / PTS_VALID flags
2       2     uint16  reserved = 0
4       4     uint32  sequence
8       8     uint64  media_pts_us
16      4     uint32  payload_length
20      N     H.264 Annex-B payload
```

The implementation bounds:

- active WebCodecs sessions;
- queue length;
- queued bytes;
- access-unit size;
- session lifetime.

Backlog fails closed rather than accumulating an unbounded delayed stream or
dropping arbitrary dependent delta frames.

## Client

The Telegram Mini App client uses:

```text
VideoDecoder
EncodedVideoChunk
optimizeForLatency=true
canvas rendering
```

The client records coded, visible and display dimensions separately and does not
assume that coded height equals visible/display height.

A manual Telegram Android WebView capability check performed before this release
confirmed:

```text
VideoDecoder=true
EncodedVideoChunk=true
VideoFrame=true
WebSocket=true
H.264 Baseline / Constrained Baseline configs supported
real Annex-B VideoFrame output observed
observed single-frame decode ~11.7 ms
```

That manual check proves the browser decoder path only. It does not yet prove
the full live camera / CloudPub WSS path.

## Canary diagnostics

The 60-second canary reports, among other values:

- WebSocket connect time;
- source startup / first source unit;
- first binary message;
- first decoded frame;
- received/decoded access units;
- keyframes and sequence gaps;
- decode p50/p95/max;
- inter-arrival p50/p95/max;
- maximum decoder queue;
- accumulated transport lag.

Accumulated lag uses relative client arrival elapsed time against relative media
PTS elapsed time, so synchronized HA/phone clocks are not required.

This is transport/decoder lag, not asserted physical camera glass-to-glass
latency.

## Existing playback remains unchanged

Release 1.7.24 does not replace the ordinary surveillance path:

```text
MSE -> WebRTC -> HLS fallback
```

and does not change the validated Comelit Entrance camera lifecycle.

The experimental WebCodecs path explicitly rejects the Comelit Entrance camera
for this phase.

## Safety

The feature PR preserves these boundaries:

```text
COMELIT_ENTRANCE_OPEN=false
COMELIT_MEDIA_STARTED=false
DOOR_ACTIONS=0
GATE_ACTIONS=0
automatic_retry=false
```

Camera source URLs, credentials, Telegram initData, cookies and internal media
credentials are not exposed to the browser or diagnostics.
