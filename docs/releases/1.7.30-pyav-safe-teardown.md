# Comelit 1.7.30 — safe WebCodecs PyAV teardown

Release 1.7.30 includes the Mini App WebCodecs lifecycle correction from
[PR #277](https://github.com/alexsudakov/comelit/pull/277).

Closing a viewer or switching tabs could cancel an asynchronous demux await
while FFmpeg continued reading, then close the same PyAV container from another
thread. A reported Home Assistant Core SIGSEGV immediately after viewer close
strongly supports this race; no native backtrace was captured.

Each H.264 source now uses one owner thread with FIFO commands for opening,
reading, packet snapshot copying, and closing the container. Cancellation queues
close behind any active read. Teardown is idempotent and bounded. Follow-up fixes
retrieve late Future errors and resolve pending requests when the owner exits,
including requests arriving during final queue draining.

The correction applies to both Entrance SDP and ordinary RTSP WebCodecs sources.
The existing WebCodecs endpoint, protocol v2, framing, PyAV read timeout,
frontend fallback policy, and Door/Gate behavior are unchanged. Release 1.7.30
introduces no native helper replacement relative to release 1.7.29.

## Validation

Merged feature commit: `1bc87c264649f3e1a1102a724a9f56c97b9bb51e`.

- 22 lifecycle test functions cover cancellation, blocked reads, late errors,
  owner termination, repeated close, bounded teardown, polling/fd guards, and
  a negative control for the former concurrent read/close pattern.
- Mini App CI on the merged feature commit: 122 tests passed.
- Offline safety and Validate HACS passed on that commit.
- The executor reports six consecutive full-suite passes and a deterministic
  RED-to-GREEN probe for the final enqueue/termination race.

Fake-PyAV tests establish serialized ownership. They do not prove that real
FFmpeg can never crash. No live camera validation was performed for this fix.

## Installation

Update to 1.7.30 through HACS and restart Home Assistant to load the corrected
Python runtime. Publishing this release does not install it or restart HA.

The ordinary-camera EOF/restart fallback policy remains a separate issue.
