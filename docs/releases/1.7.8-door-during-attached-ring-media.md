# 1.7.8 — Door during attached inbound Ring media

Status: **release-ready / physical Ring acceptance required**

## Defect

The direct Home Assistant service `comelit.open_door` rejected Door/Gate
operations whenever the supervisor reported `attached_media_busy=true`.

That guard was too broad.

A physical inbound Ring uses the attached-media lifecycle. In that mode the
existing persistent listener remains running, the current call transaction is
reused, and no second cloud/P2P session is created. The listener lineage also
preserves the validated one-shot Door handler and reuses its existing CTPP
channel.

The previous Python service guard therefore rejected a Door operation even
though the listener-owned Door path was still present.

## Fix

The service now distinguishes the two media ownership modes:

- separately bootstrapped on-demand media:
  - `media_paused=true`;
  - persistent listener is stopped;
  - Door remains fail-closed;
- attached physical Ring media:
  - persistent listener remains running;
  - current Ring transaction / CTPP is reused;
  - `comelit.open_door` is allowed to call the existing
    `runtime.async_open_door()` one-shot path.

The Door protocol implementation itself is unchanged.

## Safety invariants

- no second P2P or CTPP session is opened for the Door action;
- the existing listener CTPP is reused;
- exactly one explicit Door operation is requested;
- no automatic retry is added;
- no physical Door effect is asserted from software success alone;
- separately bootstrapped media still blocks Door while the listener is paused;
- attached media and Door remain owned by the same persistent listener runtime.

No native helper rebuild is required for this release: the attached listener
binary already contains the preserved SIGUSR1 Door entrypoint and Door tick
path. The defect was the Home Assistant service routing guard above it.

## Physical acceptance

After installing 1.7.8 and restarting Home Assistant:

1. trigger one real entrance-panel Ring;
2. allow the attached call camera to become active;
3. issue one explicit Entrance Door open action while video is still active;
4. verify that the Door request is no longer rejected solely because attached
   media is active;
5. record the software outcome and physical observation separately;
6. confirm the video/call lifecycle remains active or terminates only according
   to the existing call/media lifecycle.

Do not use this release as evidence that Door during a separately bootstrapped
manual/on-demand media session is supported. That remains intentionally
fail-closed until a same-session media-helper Door path is separately proven.
