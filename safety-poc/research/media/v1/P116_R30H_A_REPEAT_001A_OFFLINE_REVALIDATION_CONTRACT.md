## 1. Goal

Revalidate the existing R27 one-shot same-session client `0x001A` repeat proof against fresh current main and prove that the corrected research runner is bound to the generated candidate helper rather than silently falling back to the base helper.

R30H-A is preparation only. It must not contact the Comelit service/device, start a physical camera session, stop/restart the production listener, deploy anything to Home Assistant, or change the packaged production helper.

The purpose is to make one later R30H-B live attempt meaningful: if R30H-B sends one second client `0x001A` inside the already-active media session, the evidence must prove that the candidate code actually executed.

R26 classified same-session media-request refresh as plausible but blocked production implementation until repeat safety was proven live.

R27 attempted that proof, but the result is invalid for the repeat hypothesis because the candidate helper was never executed. The historical R27 result explicitly recorded:

Current main contains a corrected R27 runner that materializes a per-run wrapper, substitutes the base holder path with the candidate helper path, verifies the substitution fail-closed, and invokes the candidate wrapper. R30H-A must prove that corrected path remains valid on current main before any new live attempt.

## 7. Required offline questions

R30H-A must answer all of the following.

### A. Current-lineage generation

- Does `entrance_p116_r27_repeat_001a_transform.py` still compose from the current canonical P106/P116 generator lineage?
- Does generation from the canonical base source succeed deterministically?
- What is the generated candidate source SHA256 on fresh main?

- Does the generated candidate compile/link with the expected CT120 toolchain without adding runtime dependencies?

A stale SHA pin must be classified explicitly; do not silently update a pin until Codex proves whether source semantics changed or the pin alone is obsolete.

### B. One-shot repeat semantics

Prove statically/tests that the candidate:

- sends exactly one normal initial client `0x001A`;
- schedules at most one additional same-session client `0x001A`;
- performs the repeat only after initial ACK/signaling completion, media-active state and observed video RTP progress;
- regenerates the repeat from current semantic state rather than replaying captured bytes;
- uses a fresh sequence state for the repeat;
- reuses target/geometry/address-role semantics;
- never sends a third `0x001A`;
- performs no new ICE negotiation, PseudoTCP creation, CTPP registration, self-activation or RTPC OPEN pair;
- has bounded ACK observation and no retry loop;
- cancels repeat timers during teardown.
