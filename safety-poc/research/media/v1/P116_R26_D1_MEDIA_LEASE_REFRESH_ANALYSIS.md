## Evidence Answers

1. Which protocol message/request starts video RTP today, and which code path emits it?

   `STRONGLY_SUPPORTED`: the request that immediately precedes media active is the client CTPP `0x001A` media request. P72 defines client `0x001A` as a 60-byte CTPP media-signaling body with the video-config tag, second RTPC target binding, geometry fields, and address roles (`safety-poc/research/media/v1/P72_RTPC_CLIENT_MEDIA_GENERATION_CONTRACT.md:61`). P74 composes it after two allocator-backed RTPC OPENs (`safety-poc/research/media/v1/P74_ALLOCATOR_BACKED_RTPC_MEDIA_GENERATION.md:23`). In the runtime transform, `p76_generate_client_001a()` fills `p78_rtpc_client_001a` (`safety-poc/research/media/v1/entrance_p78_rtpc_media_live_stage_transform.py:425`), `p78_queue_rtpc_client_001a()` queues it on `v4_ctpp_channel_id` (`safety-poc/research/media/v1/entrance_p78_rtpc_media_live_stage_transform.py:280`), and P97 delays media active until after the device ACK for that client `0x001A` (`safety-poc/research/media/v1/entrance_p97_complete_post_000a_ack_cycle_transform.py:373`).

2. In which phase of the helper's lifecycle is it emitted?

   `PROVEN_STATIC`: it is emitted during the RTPC/media signaling phase, after entrance self-activation and before `P80_MEDIA_ACTIVE=true`. The base entrance sequence begins with registered CTPP self-activation and the client/device `0x0008` video event (`safety-poc/research/media/v1/entrance_self_activation_signaling_transform.py:9`). P95 inserts the pre-RTPC device-`0x0002` gate before RTPC starts (`safety-poc/research/media/v1/entrance_p95_wait_device_0002_before_rtpc_transform.py:14`). P97 then queues client `0x001A` only after the post-`000A` ACK cycle (`safety-poc/research/media/v1/entrance_p97_complete_post_000a_ack_cycle_transform.py:340`). `entrance_signal_begin_media_observation()` sets `ENTRANCE_SIGNAL_OBSERVE_MEDIA`, enables forwarding, and prints `P80_MEDIA_ACTIVE=true` only after RTPC is complete and PseudoTCP is open (`safety-poc/research/media/v1/entrance_p80_ha_media_runtime_transform.py:583`).

3. Is there an ACK/response for it, and what is that response's proven shape?

   `STRONGLY_SUPPORTED`: the initial request has a same-CTPP structural ACK gate in our runtime path. P97 arms `p97_wait_device_ack_001a`, queues client `0x001A`, and finishes only when `p97_handle_device_ack()` observes the ACK while that gate is armed (`safety-poc/research/media/v1/entrance_p97_complete_post_000a_ack_cycle_transform.py:357`, `safety-poc/research/media/v1/entrance_p97_complete_post_000a_ack_cycle_transform.py:416`). P99 changes binding to state-scoped structural ACK because exactly one outstanding client action exists while each ACK gate is armed (`safety-poc/research/media/v1/entrance_p99_state_scoped_ack_and_early_media_demux_transform.py:11`). The proven structural predicate is same CTPP request id, body length 32, prefix/action fields matching `0x1800/0x0000`, and the `0xffff` reserved words (`safety-poc/research/media/v1/entrance_p99_state_scoped_ack_and_early_media_demux_transform.py:151`). Repeat-request ACK behavior is `UNKNOWN`.

4. Can that same request be repeated without new ICE/P2P negotiation, new PseudoTCP transport, new CTPP registration, new RTPC open, new media-session, or any change of session identity?

   `UNKNOWN`: our current helper does not implement such a repeat. It statically preserves reuse of the registered CTPP and forbids a second CTPP OPEN in the initial media setup (`safety-poc/research/media/v1/P78_ENTRANCE_MEDIA_ONE_SHOT_LIVE_CLOSURE.md:16`, `safety-poc/research/media/v1/entrance_p78_rtpc_media_live_stage_transform.py:340`), and the current HA transport has only one P2P negotiation and one native process per media start (`safety-poc/tests/test_p116_r24_recovery_shim_lifecycle.py:97`). Those facts prove the initial setup boundary, not repeat safety. No repo evidence proves that another `0x001A` can be emitted later on the same CTPP, PseudoTCP, RTPC allocation, and HA media-session identity without side effects.

5. Does anything in our own evidence show a second such request inside one session, or show that a repeat is rejected/deduplicated?

   `UNKNOWN`: no second request is observed in our own evidence. The generated path has one `P78_TX_RTPC_CLIENT_001A` completion path, a `p97_client_001a_started` guard, and then media active (`safety-poc/research/media/v1/entrance_p97_complete_post_000a_ack_cycle_transform.py:340`, `safety-poc/research/media/v1/entrance_p97_complete_post_000a_ack_cycle_transform.py:373`). P116/R24 explicitly verifies that no second upstream session is introduced, but that is not a same-session media-request repeat (`safety-poc/tests/test_p116_r24_recovery_shim_lifecycle.py:97`). There is also no evidence in our lineage that a second same-session `0x001A` is rejected or deduplicated.

6. Does the 36 s video window look like a per-request grant, a device-side timer, or an upstream/idle timeout, and what in OUR evidence supports that classification?

   `PLAUSIBLE`: it looks more like a device/request-scoped media grant or device-side timer than an HA hard limit or local idle timeout, but our evidence does not prove repeat refresh. R25 observed video stopping after 34.9 seconds while the R25 media session and HA/HLS path had been valid. Earlier frozen official evidence also records a self-activation capture ending around 35 seconds (`safety-poc/research/media/v1/P77_ENTRANCE_MEDIA_OFFLINE_INTEGRATION_AND_LIVE_GAP_ANALYSIS.md:83`). HA's session hard limit is 600 seconds and is measured from successful upstream start, not extended by leases (`custom_components/comelit/media_session.py:9`, `custom_components/comelit/media_session.py:64`), so the approximately 35-second stop is not explained by HA's hard timeout. The current transport watchdog reacts after the native media process ends (`custom_components/comelit/media_session.py:272`); it does not create a 35-second upstream cutoff. Classification remains `PLAUSIBLE`, not proven.
